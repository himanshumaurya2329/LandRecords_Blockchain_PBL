📜 Deep Dive: Current Chaincode

Abhi Project Me Kaunse Chaincode Functions Hain Aur Kaise Kaam Karte Hain?

Hamare current land-registration-contract.js me 11 main functions/helpers hain. Inka ek-ek kanoon (rule) aasan Hinglish me samjhein:

1. initLedger(ctx)
Current Function Any Org / Deployer

Hyperledger Fabric standard function jo chaincode pehli baar instantiate/install hone par trigger hota hai.

📌 Kanoon / Rule:
Ye ek startup hook hai. Abhi hamare project me ye empty hai (sirf log print karta hai). Agar hum chahe toh isme shuruat me koi dummy test application initialize kar sakte hain.
2. createApplication(ctx, applicationId)
Current Function Role: applicant / admin

Naya land registration request blockchain ledger pe record karta hai.

📌 Kanoon / Rule:
1. Role Check: Sirf wahi user call kar sakta hai jiska certificate role applicant ya admin ho.
2. Duplicate Check: Agar applicationId pehle se ledger me hai toh error throw karega.
3. Transient Encryption: Sensitive citizen details (Aadhaar, Name, Property Value) normal argument me nahi, Transient Map me aate hain taaki block payload me plaintext na dikhe. Code isko AES-256-CBC se encrypt karke ledger me daalta hai.
4. Initial State: Application ka status submitted set hota hai aur history me 'created' ka pehla immutable block lagta hai.
3. verifyByRevenue(ctx, applicationId, officerDataStr)
Current Function Role: officer / admin (Org2)

Revenue Department application ki basic verification karta hai.

📌 Kanoon / Rule:
1. State Check: Application ka status compulsory submitted hona chahiye.
2. Role: Calling certificate me role officer hona chahiye.
3. Status Change: Status verified me badal jata hai, revenue verification metadata save hota hai, aur history me entry add hoti hai.
4. surveyReportUpdate(ctx, applicationId, surveyDataStr)
Current Function MSP: Org2MSP Only (Surveyor)

Zameen ka actual physical survey data (coordinates, boundary map hash) blockchain pe update karta hai.

📌 Kanoon / Rule:
1. MSP Check: Client Identity se check karta hai cid.getMSPID() === 'Org2MSP'. Koi citizen ya Org1/Org3 ka banda survey report upload nahi kar sakta.
2. Survey Attach: Application object me surveyReport attach hota hai aur immutable history me surveyor ka ID aur timestamp seal ho jata hai.
5. forwardApplication(ctx, applicationId, forwardDataStr)
Current Function Strict Multi-Tier Workflow

Hamare project ka sabse bada multi-tier government workflow engine. File ek desk se doosri desk tak electronically move karti hai.

📌 Kanoon / Rule:
Ye ek strict state machine hai jo dictionary workflowSequence follow karti hai:
• submitted / with_clerk → Sirf clerk forward karega → next status with_superintendent
• with_superintendent → Sirf superintendent → next status with_project_officer
• with_project_officer → Sirf project_officer → next status with_mro (Org2 shift)
• with_mro → mro → with_surveyor → surveyor → with_revenue_inspector → with_vro → with_revenue_dept
• with_revenue_dept → with_joint_collector (Org3 shift) → with_collector → with_ministry_welfare → approved.
Rule: Agar galat role ka user ya out-of-order forward attempt karega, smart contract transaction reject kar dega.
6. approveByCollector(ctx, applicationId, approvalDataStr)
Current Function Role: collector / admin / ministry_welfare

District Collector ya Ministry of Welfare ka final digital sign-off.

📌 Kanoon / Rule:
Application verified/processed hone ke baad District Collector final clearance deta hai. Agar call Ministry of Welfare (mw) role se aati hai toh final status completed banta hai (pukka land deed issue).
7. getApplication(ctx, applicationId)
Current Function Read-only (All Orgs)

Kisi bhi specific application ki complete details fetch karta hai.

📌 Kanoon / Rule:
Ledger se encrypted data read karta hai, decryptData() se AES-256 decipher karke JSON format me return karta hai. Saath me automatically M8 Trust Score (0-100%) aur M9 AI-OCR data calculate karke response me attach karta hai.
8. getAllLandRequest(ctx)
Current Function Read-only (All Orgs)

Ledger me moujood sabhi land applications ki list laata hai (Dashboards ke liye).

📌 Kanoon / Rule:
Fabric iterator ctx.stub.getStateByRange('', '') se range query chalata hai. Har record ko decrypt karta hai aur list bana kar frontend ko deta hai.
9. getHistory(ctx, applicationId)
Current Function Audit Trail Query

Application ka complete blockchain lifecycle audit trail nikalta hai.

📌 Kanoon / Rule:
Day-1 se lekar aaj tak kis officer ne, kis timestamp par, kya remark daal kar forward kiya, sabhi transaction IDs ke saath array me return hota hai. Ye tamper-proof proof hota hai court ya citizen ke liye.
10. recordDocumentIntegrity(ctx, docHash, ipfsHash, aadharNumber, requestId, officialId)
Current Function Org1MSP or Org2MSP

M7 Security feature: Document ka SHA-256 hash aur IPFS CID blockchain pe amar kar deta hai.

📌 Kanoon / Rule:
Deed ya survey map ka hash composite key integrity~[docHash] bana kar state me daalta hai. Agar kal ko koi PDF me 1 pixel ya 1 letter bhi badalta hai toh hash match nahi hoga aur forgery pakdi jayegi!
11. queryByStatus(ctx, status)
Current Function CouchDB Selector Query

Status ke basis pe applications filter karta hai (jaise sirf 'with_collector' ya 'submitted').

✏️ 1. createApplication() — [MODIFIED]
Modify Existing
📌 Kya Change Hoga & Rule:
Pehle single applicant ka data save hota tha. Ab hum check karenge:
• Agar ownershipType === 'joint' hai toh owners array compulsory check hoga.
• Rule 1 (Count): Minimum 2 aur Maximum 5 co-owners hone chahiye.
• Rule 2 (100% Share Total): Sabhi co-owners ke sharePercent ka jod exactly 100% hona chahiye. (e.g. 50% + 50%, ya 40% + 30% + 30%). Agar 99% ya 101% hua toh transaction throw Error karegi.
• Rule 3 (Consent Setup): Shuruat me har co-owner ka consentStatus: 'pending' aur allConsentsGiven: false set hoga. Single owner ke case me direct allConsentsGiven: true hoga taaki puraana flow break na ho!
• Rule 4 (Dispute Flag): Initial isDisputed: false hoga.
✏️ 2. forwardApplication() — [MODIFIED]
Modify Existing
📌 Kya Change Hoga & Rule:
Function ke shuruat me do Iron-Clad Guards (Kanooni Suraksha Kawach) lagaye jayenge:
• Guard 1 (Dispute Check): Agar application.isDisputed === true hai, toh koi bhi officer application ko aage forward nahi kar sakta! Error aayega: "Application is FROZEN due to active dispute. Contact Collectorate."
• Guard 2 (All Consents Required): Agar ownershipType === 'joint' hai aur allConsentsGiven !== true hai, toh application Clerk/Superintendent ke desk par aage nahi badhegi! Error aayega: "Cannot forward: Pending co-owner consents: [Ramesh, Suresh]".
✨ 3. addCoOwnerConsent(ctx, applicationId, ownerId, consentDataStr)
New Function Co-Owners Individually
📌 Kanoon / Rule:
Jab Primary applicant application submit kar deta hai, toh baaki co-owners ko apne account se login karke consent sign karna hota hai.
• Calling user ka ownerId check hota hai ki wo owners[] list me hai ya nahi.
• Agar pehle se approved hai toh reject hoga (no double consent).
• Us owner ka consentStatus = 'approved' aur timestamp ledger me seal ho jayega.
• Smart contract turant check karega: Kya ab sabhi owners ka consent 'approved' ho gaya?
• Agar HAAN, toh automatic allConsentsGiven = true ban jayega, aur ab application forward hone ke liye unlock ho jayegi!
✨ 4. transferOwnershipShare(ctx, applicationId, fromOwnerId, toOwnerId, sharePercent, ...)
New Function Property Owner (Org1MSP)
📌 Kanoon / Rule:
Kal ko agar co-owner apna 20% ya 50% hissa kisi aur ko bechna ya gift karna chahta hai:
• Rule 1: Property ka status compulsory completed (registered) hona chahiye. (Processing ke beech me hissa nahi bik sakta).
• Rule 2: Property freeze ya dispute me nahi honi chahiye (!isDisputed).
• Rule 3: fromOwnerId ke paas utna share hona chahiye jitna wo transfer kar raha hai.
• Rule 4: Naye ya existing co-owner me share add hoga, aur transaction ke baad bhi total exactly 100% rehna chahiye.
✨ 5. raiseOwnershipDispute(ctx, applicationId, raisedBy, reason)
New Function Any Listed Co-Owner
📌 Kanoon / Rule:
Maan lo do bhaiyon me jhagda ho gaya ki "Mera share 50% tha par application me 30% likha hai":
• Koi bhi listed co-owner ye function call kar sakta hai.
• Contract verify karega ki raisedBy waqai me property ka co-owner hai.
• Smart contract turant application.isDisputed = true kar dega aur reason + timestamp record karega.
• Iske baad pura application FREEZE ho jayega. Koi bhi revenue officer ya collector isko aage forward ya approve nahi kar sakta!
✨ 6. resolveOwnershipDispute(ctx, applicationId, resolutionDataStr)
New Function 🔑 Org3MSP Collector Only
📌 Kanoon / Rule:
Dispute kaun suljhayega? Org3 (Collectorate / District Collector).
• Contract strictly check karta hai: if (mspId !== 'Org3MSP') throw new Error(...).
• Collector dono pakshon ki baat sunkar formal resolution decision record karta hai.
• isDisputed = false ho jata hai aur file wapas UNFREEZE ho kar normal workflow me aa jati hai.
✨ 7. getOwnershipDetails(ctx, applicationId)
New Query Function Read-only (All Orgs)
📌 Kanoon / Rule:
Frontend dashboard ke liye fast read query. Ye ek clean object return karega jisme sabhi owners, unke percentage shares, kiska consent aa chuka hai (approved), aur kiska baki hai (pending) saaf-saaf dikhta hai.
⚖️ Legal & Governance Process

Dispute Freeze Aur Resolution Process: Kise Adhikar Hai Aur Kaise Solve Hoga?

Aapne pucha: "Agar koi co-owner dispute raise kare toh freeze hoga, but resolve kaise hoga aur kaun karega?"

⚠️ Phase 1: Freeze Kaise Hota Hai?

  • Koi bhi listed co-owner (jiski ID owners[] me hai) call karega raiseOwnershipDispute(applicationId, raisedBy, "Share percentage incorrect").
  • Blockchain ledger par isDisputed = true set ho jata hai.
  • History me transaction seal ho jati hai with official dispute tag.
  • Effect: forwardApplication() me laga hua Guard 1 turant activate ho jata hai. Ab Registration Clerk, Revenue Inspector, ya Tehsildar chah kar bhi is file ko aage forward nahi kar sakte!

⚖️ Phase 2: Kaun Resolve Karega Aur Kyun?

Adhikar: Sirf Org3 (Collectorate / District Collector / Joint Collector) ko adhikar hai. Chaincode me check hai: cid.getMSPID() === 'Org3MSP'.
Kyun Sirf Org3?
Real-world Indian Revenue Administration me:
1. Org1 (Registration Department): Sirf document register karne wala clerk office hai, inke paas dispute sunne ka kanooni adhikar nahi hota.
2. Org2 (Revenue Department): Field inspection aur survey karta hai.
3. Org3 (District Collectorate): District ka sarvoch Quasi-Judicial Revenue Court hota hai. Kisi bhi land title ya share dispute ka faisla Collector / Joint Collector hi sunata hai.

🔍 Phase 3: Resolution Kaise Execute Hota Hai?

  1. Inquiry Hearing: Collector dono co-owners ke documents aur claim sunta hai (off-chain / digital inquiry).
  2. Decision Draft: Collector resolution summary banata hai (e.g. "Hearing completed on 29-Sep-2026. Both co-owners agreed to 50-50 share deed order #DC/REV/402").
  3. On-Chain Resolution: Collector Org3 identity se resolveOwnershipDispute(applicationId, resolutionData) call karta hai.
  4. State Reset: isDisputed = false ho jata hai aur resolvedAt timestamp stamp ho jata hai.
  5. Unfreeze: Ab application wapas normal flow me unlock ho jati hai aur aage forward ho sakti hai!
Collector's Chaincode Resolution Log
application.isDisputed = false;
application.disputeDetails.resolvedAt = timestamp;
application.disputeDetails.resolution = resolution.decision;
application.disputeDetails.resolvedBy = "collector_user";

application.history.push({
  action: 'dispute_resolved',
  remarks: 'Dispute resolved. Application UNFROZEN.'

❓ Member 1 Deep Q&A

Deep Doubts Clarified: Share Rectification & Sale Verification

Aapne jo do technical aur governance doubts puche hain, wo real-world land administration aur blockchain smart contracts ke sabse crucial edge cases hain. Inka detailed explanation dekhein:

DOUBT 1

Co-Owner Dispute Me Form Entry Direct Update Hoti Hai Ya Form Reject Hokar Naya Banta Hai?

Scenario: Ek co-owner ne dispute raise kiya: "Mera share 50% tha, par form me galti se 30% likha hai." Collector ne sunwayi ki aur user ki baat maante hue 50% share dene ka faisla kiya. Toh kya existing form ki share % entry update hogi ya form reject hoga?

✅ Option A (Recommended): Direct On-Chain Rectification Order
Kaise Hota Hai: Collectorate (Org3) ke paas Quasi-Judicial Revenue Court ki power hoti hai. Collector ek Rectification Order (Durusti Aadesh) pass karta hai.

Smart contract function resolveOwnershipDispute(applicationId, resolutionData) me Collector corrected shares pass karta hai:
resolutionData = { decision: "Share corrected to 50%", updatedOwners: [...] }.

Kyun Best Hai?
  • Pehle se complete ho chuki Surveyor Inspection Report aur Field Map bekar nahi hoti.
  • Citizen ko dobara registration fees aur lambe line me nahi lagna padta.
  • Blockchain ledger par tamper-proof audit trail banta hai: shuru me 30% tha, dispute hua, Collector ka order number laga, aur ab 50% ho gaya!
❌ Option B (Strict Fraud Case): Hard Rejection & Fresh Filing
Kaise Hota Hai: Agar Collector ko pata chale ki Primary Applicant ne forgery ya fraud kiya hai aur dono paksh aapas me raazi nahi hain:

Collector application ka status direct application.status = 'rejected' kar deta hai.

Iska Asar:
  • Puraani application hamesha ke liye rejected mark ho jati hai (audit trail blockchain par rehta hai).
  • Applicants ko saare co-owners ke signature ke saath ek Fresh Joint Application shuru se submit karni padti hai.
💡
Hamara Smart Contract Dono Support Karega!
Hamare resolveOwnershipDispute function me Collector dono options choose kar sakta hai:
Agar resolutionData.action === 'rectify_shares' hai, toh contract automatically application.owners array ko update karke application ko UNFREEZE kar dega taaki workflow smoothly aage badh sake!
DOUBT 2

Jab Ek Co-Owner Apna Share Kisi Naye Ya Doosre Co-Owner Ko Bechega, Toh Kya Verification Hogi Ya Direct Transfer?

Question: Kya land share Bitcoin ya Crypto token ki tarah 1-click me wallet-to-wallet transfer ho jata hai, ya koi legal verification process run hoti hai?

⚠️
Golden Rule: Zameen Crypto Token Nahi Hai!
Zameen physical property hai. Agar bina verification direct transfer allow kar diya jaye, toh koi bhi hacker ya be-imaan co-owner family ki zameen kisi gunde ya ajnabi (stranger) ke naam transfer kar dega. Isliye land law me Verification Pipeline Mandatory hoti hai!

Case 1: Naye Person (Third Party) Ko Bechna

  1. Identity & KYC Check: Naye khareeddar (Buyer) ka Aadhaar / DigiLocker verification compulsory hoga.
  2. Right of Pre-emption (Haq-e-Shufa / Co-Owners NOC): Indian Land Law ke mutabiq parivarik ya joint land me baaki co-owners ko pehla haq hota hai. Isliye baaki co-owners ka Digital NOC / Approval smart contract par record hota hai.
  3. Deed Registration (Org1): Org1 Sub-Registrar stamp duty aur sale deed verify karta hai. Uske baad hi ledger me naya owner add hota hai.

Case 2: Kisi Existing Co-Owner Ko Transfer Karna

  1. Relinquishment Deed (Haq-Tyag Patra): Selling co-owner apna hissa doosre maujuda bhai/partner ke naam relinquish karta hai.
  2. Co-Owner Mutual Consent: Dono parties (Seller & Buyer) digital signature se transaction confirm karte hain.
  3. Mathematical Invariant: Smart contract strictly verify karta hai:
    seller.share >= transferShare
    Aur transfer ke baad bhi sabhi owners ka total exactly 100% rehta hai.
